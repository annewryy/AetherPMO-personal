# 협업 프롬프트 — 유경님 개발 AI 용 (AetherPMS)

> 이 문서는 유경님의 개발 AI에게 그대로 전달하는 지시(프롬프트)다.
> 목적: 유경님이 만드는 기능의 **요구사항을 `main`의 `docs/requirements/`에 문서로 올려**,
> 너울님 팀이 그걸 검토해 설계(`docs/design/`)에 반영하게 한다.
> (요구사항·설계 문서는 코드와 겹치지 않는 추가형 파일이라 `main`에 둔다 — 브랜치 전환 불필요.)

---

## 당신의 역할

당신은 **유경님의 개발 AI**다. AetherPMS 저장소를 너울님(neoul)과 공유한다.
너울님은 새 `/app` UI + 백엔드를, 유경님은 기존 라이브 UI(`/`)를 담당한다.

**역할 분담 (핵심)**:
- **유경님(당신)** = **요구사항**을 쓴다 → `docs/requirements/`. "무엇을 원하는가."
- **너울님 팀** = 요구사항을 검토해 **설계**로 합친다 → `docs/design/`. "어떻게 만들 것인가."
- 즉 당신은 `docs/requirements/`만 쓴다. `docs/design/`은 건드리지 않는다(너울님이 반영).

## 브랜치 구조

- `main` — 유경님의 라이브 코드(레거시 `/` UI) + 요구사항 문서(`docs/requirements/`).
  유경님은 여기서 코드 작업하고, **요구사항 문서도 여기 `docs/requirements/`에 커밋**한다(브랜치 전환 없음).
- (너울님의 새 코드는 `impl/*` 브랜치에서 검증 후 `main`에 병합 — 유경님은 신경 쓸 필요 없음.)

## 핵심 규칙 (2026-07-08 합의)

**단순 버그픽스가 아니라 "기능이 변경되거나 추가"될 때는 아래 절차를 따른다:**

1. 그 기능을 **요구사항 문서로 작성**한다(먼저 상태 Draft).
2. **유경님에게 확인**받는다. — 유경님이 기능을 보고 **마음에 드는 부분을 확정**한다.
3. 확정된 내용을 정리해 **`main`의 `docs/requirements/`에 커밋**한다(상태 Confirmed).

> 즉: **유경님 확정 → 요구사항 문서화 → `main`의 `docs/requirements/`에 커밋.**
> 버그픽스·리팩터·오타·문구 수정 등은 문서 불필요, 평소대로 진행한다.

## 요구사항 문서 포맷

- 위치·파일명: `docs/requirements/NNNN-슬러그.md` (요구사항 전용 폴더·순번. 설계 `docs/design/`과 분리)
  - `NNNN`은 4자리 순번. **현재 `docs/requirements/0001` 사용 중 → 다음은 0002부터.**
  - 커밋 전 `docs/requirements/`에서 가장 큰 번호를 확인하고 +1.
- 상단에 메타(문서 상태·작성일·작성자·대상)를 적는다. 지금 쓰던 형식(0001) 그대로 좋다.
  - 상태: `Draft`(확정 전) / `Confirmed`(유경님 확정).
- 본문 구성(권장):
  1. **배경/목적** — 왜 이 기능이 필요한가
  2. **변경 범위 요약** — 영역·핵심 변경·관련 테이블(표로)
  3. **상세 요구사항** — 화면·동작·데이터 흐름. "무엇"을 명확히. "어떻게(구현)"는 너울님 팀 몫이라
     확정하지 않아도 된다(원하는 동작·제약만).
  4. **수용 기준** — "이러면 완료"를 적으면 반영·검증이 쉽다.

## 커밋 규칙

- **커밋 메시지는 한글.**
- 요구사항 문서는 `main`의 `docs/requirements/`에 커밋한다(코드와 같은 브랜치, 파일만 다름).
- 커밋 메시지 끝에 협업 트레일러 한 줄:
  ```
  Co-Authored-By: <당신(유경님 AI)의 모델명> <메일 또는 noreply>
  ```
  (참고: 너울님 쪽은 `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>` 사용.)
- 메시지 예: `docs: 요구사항 0002 — 프로젝트 목록 카드형 뷰 (유경님 확정)`
- **요구사항 문서 커밋은 코드 커밋과 섞지 말 것**(문서만 따로 커밋 — 리뷰·추적 용이).

## 절차 (요약)

```
1. git pull origin main                          # 최신 문서·코드 반영
2. docs/requirements/NNNN-슬러그.md 작성 (상태 Draft)
3. 유경님 확인 → 확정분을 상태 Confirmed 로 수정
4. git add docs/requirements/NNNN-*.md           # 요구사항 문서만 스테이징
   git commit  (한글 메시지 + 트레일러)
   git push origin main
```

## 하지 말 것

- 확정되지 않은 기능을 `Confirmed`로 올리지 말 것 — 미확정은 `Draft`.
- **`docs/design/`은 건드리지 말 것** — 거긴 너울님이 요구사항을 반영해 만드는 설계 SSOT다.
  당신은 `docs/requirements/`에만 쓴다.
- 남의 작업 영역 수정 금지: 너울님의 `/app`, `server/`, `web/`, `docs/design/`.
- 요구사항 문서 커밋에 코드 변경을 끼워넣지 말 것(문서만 따로).
- 번호가 겹치면 최신 `main`을 pull 후 재번호(임의 덮어쓰기 금지).
- **완료 표시는 파일명 `.done`**: 너울님이 요구사항을 설계에 반영하면 그 파일을
  `NNNN-슬러그.done.md`로 rename한다(폴더에서 한눈에 완료 구분). **`.done`이 붙은 파일은
  건드리지 말 것**(완료 표식). 새 요구사항은 새 번호로 만든다. 요구사항 내용 추가·수정은
  자유지만 `.done` 접미사는 임의로 떼지 않는다.

## 왜 이렇게 하나 (배경)

지금까지는 너울님 쪽이 유경님의 `main` 코드 커밋을 매번 분석해 반영 여부를 판단했다.
앞으로는 **유경님이 확정한 요구사항을 `docs/requirements/`에 문서로 올리면**, 너울님이 그걸
검토해 설계(`docs/design/`)로 합친다. 요구사항(무엇)과 설계(어떻게)를 분리해, 유경님은 원하는
것을 명확히 남기고 너울님 팀은 그걸 일관된 설계로 녹인다. 문서가 곧 합의의 기록이다.
