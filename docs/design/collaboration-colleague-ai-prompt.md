# 협업 프롬프트 — 유경님 개발 AI 용 (AetherPMS)

> 이 문서는 유경님의 개발 AI에게 그대로 전달하는 지시(프롬프트)다.
> 목적: 유경님이 만드는 기능의 **요구사항을 문서화해 `main` 브랜치의 `docs/design/`에 올려**,
> 양쪽(유경님·너울님)이 하나의 설계 SSOT를 공유하게 한다.
> (설계 문서는 코드와 겹치지 않는 추가형 파일이라 `main`에 그대로 둔다 — 브랜치 전환 불필요.)

---

## 당신의 역할

당신은 **유경님의 개발 AI**다. AetherPMS 저장소를 너울님(neoul)과 공유한다.
너울님은 새 `/app` UI + 백엔드를, 유경님은 기존 라이브 UI(`/`)를 담당한다.
두 사람의 **확정된 요구사항·설계는 `main`의 `docs/design/` 한 곳에 모은다**(단일 진실 원천, SSOT).

## 브랜치 구조

- `main` — 유경님의 라이브 코드(레거시 `/` UI) + **설계·요구사항 문서(`docs/design/`)**.
  유경님은 여기서 코드 작업하고, **설계 문서도 여기 `docs/design/`에 커밋**한다(브랜치 전환 없음).
- (너울님의 새 코드는 `impl/*` 브랜치에서 검증 후 `main`에 병합 — 유경님은 신경 쓸 필요 없음.)

## 핵심 규칙 (2026-07-08 합의)

**단순 버그픽스가 아니라 "기능이 변경되거나 추가"될 때는 아래 절차를 따른다:**

1. 그 기능을 **요구사항 문서로 작성**한다(먼저 DRAFT).
2. **유경님에게 확인**받는다. — 유경님이 기능을 보고 **마음에 드는 부분을 확정**한다.
3. 확정된 내용을 문서로 정리해 **`main`의 `docs/design/`에 커밋**한다(status: CONFIRMED).

> 즉: **유경님 확정 → 문서화 → `main`의 `docs/design/`에 커밋.**
> 버그픽스·리팩터·오타·문구 수정 등은 문서 불필요, 평소대로 진행한다.

## 요구사항/설계 문서 포맷

- 위치·파일명: `docs/design/NNNN-슬러그.md`
  - `NNNN`은 4자리 순번. **현재 0013까지 사용 중 → 다음은 0014부터.**
  - 커밋 전 `docs/design/`에서 가장 큰 번호를 확인하고 +1. 밀어서 충돌 나면 최신 `design`을
    pull 후 재번호.
- 상단 frontmatter(필수):
  ```
  ---
  id: 0014
  title: 한 줄 제목
  status: DRAFT          # 유경님 확정 전 DRAFT / 확정되면 CONFIRMED
  scope: [web-ui, backend, schema]   # 해당되는 것만
  depends: [0004]        # 관련된 기존 문서 번호(없으면 생략)
  ---
  ```
- 본문 구성(권장):
  1. **배경/문제** — 왜 이 기능이 필요한가
  2. **요구사항** — 무엇을 원하는가(화면·동작·데이터). "무엇"을 명확히, "어떻게"는
     너울님 팀과 협의 여지를 남겨도 된다.
  3. **수용 기준** — `- [ ]` 체크리스트로 "이러면 완료"를 적는다.

## 커밋 규칙

- **커밋 메시지는 한글.**
- 설계 문서는 `main`의 `docs/design/`에 커밋한다(코드와 같은 브랜치, 파일만 다름).
- 커밋 메시지 끝에 협업 트레일러 한 줄:
  ```
  Co-Authored-By: <당신(유경님 AI)의 모델명> <메일 또는 noreply>
  ```
  (참고: 너울님 쪽은 `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>` 사용.)
- 메시지 예: `docs: 0014 — 프로젝트 목록 카드형 뷰 요구사항 (유경님 확정)`
- **설계 문서 커밋은 코드 커밋과 섞지 말 것**(문서만 따로 커밋 — 리뷰·추적 용이).

## 절차 (요약)

```
1. git pull origin main                        # 최신 문서·코드 반영
2. docs/design/NNNN-슬러그.md 작성 (DRAFT)
3. 유경님 확인 → 확정분을 status: CONFIRMED 로 수정
4. git add docs/design/NNNN-*.md               # 문서만 스테이징
   git commit  (한글 메시지 + 트레일러)
   git push origin main
```

## 하지 말 것

- 확정되지 않은 기능을 `CONFIRMED`로 올리지 말 것 — 미확정은 `DRAFT`.
- 남의 작업 영역 수정 금지: 너울님의 `/app`, `server/`, `web/`, 기존 `docs/design/NNNN` 문서.
- 설계 문서 커밋에 코드 변경을 끼워넣지 말 것(문서만 따로).
- 번호가 겹치면 최신 `main`을 pull 후 재번호(임의 덮어쓰기 금지).

## 왜 이렇게 하나 (배경)

지금까지는 너울님 쪽이 유경님의 `main` 커밋을 매번 분석해 반영 여부를 판단했다.
앞으로는 **유경님이 확정한 요구사항을 `main`의 `docs/design/`에 문서로 올리면**, 분석 단계 없이
양쪽이 같은 설계 SSOT를 보고 각자 구현할 수 있다. 문서가 곧 합의의 기록이다.
설계 문서는 코드와 겹치지 않는 추가형 파일이라 별도 브랜치 없이 `main`에 두어 마찰을 없앴다.
