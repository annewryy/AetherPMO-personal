# 0033 — 알림 기준 정리 (사용자별 알림 트리거·수신자 판정)

- 상태: **확정·구현 완료(2026-07-27)** — 아마란스·자체 로그인 무관 수신(person 축), 1~3차 일괄 시행(impl/0037)
- 선행: 0012(코멘트·알림 v1), 0031(자체 로그인), 0032(person 연결·참여 스코프)

## 1. 현재 상태 진단

**있는 것**: `pms_notification` 테이블, 상단바 벨, `GET /api/notifications`(미읽음 우선)·
읽음/전체읽음 API, 코멘트 작성 시 알림 2종 — **MENTION**(멘션된 사용자), **REPLY**(부모 코멘트 작성자).

**공백 2가지**:
1. **트리거가 코멘트 2종뿐** — 태스크 할당, 담당 지정, 상태 전이, 마감 임박 등은 알림이 없다.
2. **수신자 식별 축이 끊겨 있다** — 알림 수신자(`recipient_uid`)와 행위자(`CurrentActor`)가
   구 데모 헤더 `X-User-Id`(uuid) 기준. 자체 로그인(0031) 전환 후 세션 사용자는 uuid가 없으므로
   **로그인 사용자에게는 알림이 생성되지도, 조회되지도 않는다**(dev 알림 0건이 그 증거).
   0005 §G에서 "행위자 승격은 별도 배치" 로 보류해 둔 잔여 항목.

## 2. 선행 결정 — 신원 축 통일 (§G 잔여 이행)

- **행위자(actor)**: `CurrentActor`를 세션(AuthContext) 사용자로 승격.
  `actor_uid` 대신 `actor_user_id`(pms_user) + 표시명. X-User-Id는 폴백(개방 모드)으로만.
- **수신자(recipient)**: `recipient_person_id` 기준으로 전환(마이그레이션으로 컬럼 추가).
  이유: 담당자·참여인력·조직이 모두 person 축(0032 §2)이고, 계정(pms_user)은 person에 연결되므로
  "담당자로 지정된 사람"을 알리려면 person이 자연 키다. 조회 시 `person_id = 내 계정의 person_id`.
- **이름→person 판정**: 담당 지정이 이름 문자열(assignee_name)이므로 0032와 동일하게
  **프로젝트 참여인력 중 동명 1인 매칭**(우선) → 전체 person 동명 1인 매칭 → 실패 시 알림 생략(오발송 방지).

## 3. 알림 트리거 기준 (제안)

| # | type | 트리거 | 수신자 | 비고 |
|---|---|---|---|---|
| 1 | `ASSIGNED` | 태스크·액션아이템·이슈(리스크)·산출물의 담당자(assignee/owner/author)가 **나로 지정·변경**됨 | 새 담당자 | 지정 해제·타인으로 변경은 이전 담당자에게 알리지 않음(소음 방지) |
| 2 | `PROJECT_ASSIGNED` | 참여인력으로 **프로젝트에 투입 등록**됨(수동 등록 + 담당 지정 자동 등록 포함) | 등록된 인력 | PM 플래그면 문구에 "PM으로" 표기 |
| 3 | `MENTION` | 코멘트에서 @멘션됨 | 멘션 대상 | 현행 유지(수신자 축만 교체) |
| 4 | `REPLY` | 내 코멘트에 답글 | 부모 코멘트 작성자 | 현행 유지 |
| 5 | `COMMENT_ON_MINE` | **내 담당 항목**(태스크·액션·이슈·산출물)에 코멘트가 달림 | 그 항목의 담당자 | 멘션·답글로 이미 알림된 사람은 제외(중복 억제) |
| 6 | `STATUS_CHANGED` | 내 담당 항목의 워크플로 **상태 전이**(산출물 반려·승인, 이슈 완료 등) | 담당자 | v1은 **반려(REJECTED)만** — 승인·완료까지 넣으면 소음. 후속 확대 |
| 7 | `DUE_SOON` / `OVERDUE` | 담당 항목 마감 **D-1·당일 / 기한 경과** | 담당자 | 일 1회 배치(§4). 같은 항목엔 미읽음 1건만 유지 |
| 8 | `RULE_RISK` | 신호 규칙 발동으로 **리스크 자동 등록**(CREATE_RISK) | 해당 프로젝트 PM | 0007 §3의 owner 지정과 세트 |

**공통 정책**
- 본인 행위는 본인에게 알리지 않는다(전 트리거).
- 중복 억제: 같은 (수신자, type, entity) 에 **미읽음이 이미 있으면 새로 만들지 않고 갱신**(created_at·preview만 갱신).
- 알림은 부가 효과 — 알림 생성 실패가 본 트랜잭션(수정·코멘트)을 실패시키지 않는다(try-catch 후 로그).
- 보존: 읽음 90일 경과분 배치 삭제(후속).
- 권한: 알림 목록은 본인 것만(세션 기준) — RBAC 스코프와 무관하게 자기 수신함만 조회.

## 4. 실행 지점

- 1·2·6: 해당 쓰기 서비스(WorkSurface·Deliverable·Member·Transition)에서 동기 삽입(§3 정책 준수).
- 5: CommentService 확장(현행 MENTION/REPLY 뒤에 담당자 판정 추가).
- 7: `POST /api/signals/evaluate` 일 1회 실행에 편승(스케줄 동일) — 별도 스케줄러 불필요.
- 8: SignalEngine CREATE_RISK 경로에 삽입.
- 프론트: 상단바 벨 배지(미읽음 수) + 목록에서 클릭 시 해당 항목 상세로 이동 — 기존 화면 계약 유지.

## 5. 단계 제안

- **1차**(수직 슬라이스): §2 신원 축 통일 + ①담당 지정 ③멘션 ④답글 (기존 2종 교체 포함) + 벨 배지.
- **2차**: ②투입 등록, ⑤내 항목 코멘트, ⑥반려.
- **3차**: ⑦마감 배치, ⑧규칙 리스크, 보존 정책, 개인별 알림 설정(끄기/켜기 — 상단바 "알림 설정" 실구현).
