# 신규 프론트 Phase 1 (web/ → /app)

## 배경
동료의 기존 UI(루트 index.html/app.js)는 `/`에서 그대로 유지하고, 신규 Vue 프론트는
`/app` 경로로 공존한다(vercel.json rewrite + vite base '/app/' — 이미 구성됨).
스캐폴딩·dataClient·타입은 이미 존재. 이 문서는 **Phase 1 화면**을 정의한다.

## 불변 계약 (워커가 반드시 지킬 것)
1. **컴포넌트는 `supabase.from(...)`을 직접 호출하지 않는다.** 데이터 접근은 오직
   `web/src/lib/dataClient.ts` 함수로. 새 조회가 필요하면 dataClient에 메서드를 추가한다.
2. 도메인 모델은 `web/src/types.ts`. DB 컬럼명(snake_case)은 dataClient 매퍼 안에만 존재.
3. 루트의 동료 파일(index.html, app.js, style.css)은 **절대 수정하지 않는다**.
4. **데이터 접근의 정본은 백엔드(0003)다.** dataClient는 `window.API_BASE`가 설정되면
   백엔드 API를 호출하고(응답은 도메인 모델 그대로), 없으면 Supabase **읽기** 폴백으로
   동작한다(과도기 개발 편의). 쓰기 기능은 백엔드 전용 — API_BASE 없으면 비활성
   표시(에러 아님). Supabase 직접 쓰기 경로는 만들지 않는다.

## 추가 인프라
- **vue-router** 도입. `createWebHistory('/app/')` — 딥링크는 vercel rewrite가 처리.
- 상태관리는 v1에선 도입하지 않는다(화면 로컬 ref + dataClient 호출로 충분). 필요해지면 Pinia.

## Phase 1 화면 (Supabase 읽기 직결 — 백엔드 없이 동작)

### P1-1 프로젝트 목록 `/app/projects` (기본 라우트)
- dataClient.projects.list() 사용(구현 완료)
- 컬럼: 코드, 이름, 단계(stage 뱃지: BIDDING 노랑/EXECUTION 초록/COMPLETED 회색),
  상태, 진행률(바), 고객사, 원본(입찰) 링크(sourceProjectId → 해당 상세로)
- 필터: 단계(전체/입찰/수행/완료), 텍스트 검색(이름·코드)
- 행 클릭 → 상세

### P1-2 프로젝트 상세 `/app/projects/:id`
- 상단: 개요(코드/이름/단계/상태/기간/고객사/계약금액/진행률) + 컨소시엄 목록
- sourceProjectId 있으면 "원본 입찰 프로젝트" 링크 카드
- **탭 구성은 프로젝트 단계(stage)에 따라 다르다** (2026-07-07 개정 — 동료 버전 패턴 계승):
  - 공통: 개요(컨소시엄 요약 포함) | 활동로그
  - **BIDDING**: 제안 태스크(입찰 단계 태스크→산출물 트리 — 테일러링 전개분.
    카탈로그 상세 패널과 동일 문법) | 컨소시엄(상세) | VRB
  - **EXECUTION**: 산출물 | 회의록 | 이슈/리스크 | 액션아이템 | 공문
  - dataClient 추가: `tasks.listByProject(projectId)`(pms_task — API 모드는
    GET /api/projects/:id/tasks)
- (기존 "탭 7종 고정" 규정은 폐기)
  — 각각 dataClient의 해당 list()를 projectId로 필터해 테이블 표시
  (dataClient에 `listByProject(projectId)` 계열 추가. VRB는 `vrb.getByProject`,
  활동로그는 `activities.listByProject` — pms_vrb_info / pms_audit_log)
- 산출물 탭: 상태 뱃지(WF-1 색상: DRAFT 회색/SUBMITTED 파랑/UNDER_REVIEW 노랑/
  REJECTED 빨강/APPROVED 초록)
- VRB 탭: 상신 상태(미상신/상신예정/상신완료/승인/반려)·예정/상신/승인일·VRB번호·메모
- 공문 탭: 문서번호·제목·구분(품의문/공문)·기안부서/기안자·현재 상태.
  결재라인 상세는 아마란스 전자결재 연계(0005 이후) — v1은 저장된 값 표시만

### P1-3 템플릿 카탈로그 `/app/catalog` — ⚠️ 동료 버전과 다름(아래 차이 섹션)
**템플릿 = 프로세스 + 프로세스별 상태전이 + 산출물의 묶음**이다. 화면은 이 3요소를
모두 드러내야 하며, 산출물 파일 목록으로 바로 점프하지 않는다.

**레이아웃: 마스터-디테일 3열** (2026-07-07 개정 — 인라인 워크플로 표시 폐기)
- 1열 분류(PHASE: 사업준비/착수계획/실행통제/종료) 선택
- 2열 프로세스 트리: ACTIVITY → TASK, 산출물은 TASK 하위(파일 평면 나열 금지).
  트리 노드는 **구조 정보만** 표시(code·name·is_optional·산출물 개수) —
  워크플로 체인·조건 뱃지를 트리에 인라인으로 그리지 않는다(시끄러움 + 오해 유발)
- 3열 **상세 패널**: TASK 또는 DELIVERABLE 클릭 시 표시
  - TASK 선택: 기본정보(코드/이름/필수여부/소속 경로) + **소속 산출물 목록**
    (이름·필수여부·파일/버전 컬럼은 '아마란스 연동 예정' 표기) + 태스크 워크플로
    다이어그램 + 산출물 공통 워크플로 다이어그램
  - DELIVERABLE 선택: 기본정보 + 소속 TASK 링크 + 산출물 워크플로 다이어그램

**워크플로 = 상태머신 다이어그램 (단방향 화살표 나열 금지)**
실제 흐름은 분기(검토중→승인｜보완요청)와 역방향(보완요청→재제출→검토중)이 있는
그래프다. 반드시 이를 드러낼 것:
- SVG 자체 렌더(라이브러리 금지). 상태 수가 5~6개라 수동 레이아웃로 충분:
  **주 흐름(초기→최종)은 위→아래 세로 일렬** — 상세 패널 폭이 좁으므로
  **가로 스크롤 금지**(2026-07-07 피드백). 스크롤이 필요하면 세로만.
  분기 전이는 오른쪽 곡선, **역방향 전이는 왼쪽 곡선**으로 구분.
  SVG는 컨테이너 폭 100%에 맞춤(viewBox). 상태 노드는 category 색
  (TODO 회색/IN_PROGRESS 파랑·노랑/DONE 초록, REJECTED 빨강), is_initial/is_final 시각 구분
- 엣지 라벨 = 전이명. **조건(guard)이 있는 전이는 🔒N 표시**
- 다이어그램 아래 **전이 목록 표**: `현재 상태 → 다음 상태 | 전이명 | 조건(사람 문장)`
  — 조건은 error_message를 그대로 노출(예: "제출하려면 산출물 파일을 1개 이상
  첨부하세요"). 뱃지 숫자만으로는 의미 전달 실패(2026-07-07 사용자 피드백)
- 데이터는 기존 `workflows.list()` 재사용(추가 쿼리 불필요)

### P1-1.5 대시보드 `/app/dashboard` (동료 UI 계승)
- KPI 카드 5종: 진행중 / 지연 / 오픈 리스크·이슈 / 미결 액션아이템 / 오늘 마감
- 프로젝트 진행률 차트(가로 바), 사업유형 분포 도넛(SVG 직접 — 차트 라이브러리 금지)
- 프로젝트 요약 테이블(이름/단계/상태/진행률/PM) — 행 클릭 시 상세로
- 데이터는 전부 기존 dataClient list() 재사용(신규 쿼리 없이 클라이언트 집계)
- ※ 동료 버전의 AI 포털(헬스스코어·리스크예측·PM추천)은 **의도적으로 제외** — 반영 안 함

### P1-4 산출물 템플릿 검색 `/app/catalog/deliverables`
- 전체 DELIVERABLE 노드를 **평면 목록 + 텍스트 검색**(name·code)으로 모아보는 별도 메뉴
- 각 행에 소속 경로 표시: PHASE > ACTIVITY > TASK (breadcrumb) — 행 클릭 시
  P1-3의 해당 위치로 이동(트리 펼침)
- P1-3(프로세스 중심)과 P1-4(산출물 중심)는 같은 데이터의 두 뷰다.
  dataClient 호출은 catalog.tree() 재사용(별도 쿼리 금지)

### P1-5 전역 횡단 목록 (동료 UI 계승 — PMO는 전체 프로젝트를 가로질러 본다)
- `/app/issues` · `/app/action-items` · `/app/official-docs` · `/app/meeting-minutes`
- 모든 프로젝트의 해당 항목을 한 테이블로: 프로젝트 컬럼 포함, 프로젝트/상태 필터 +
  텍스트 검색. 행 클릭 시 소속 프로젝트 상세의 해당 탭으로 이동
- 기존 dataClient 전체 list() 재사용(이미 전 프로젝트 조회임)
- 사이드바 네비게이션: 대시보드 | 프로젝트 | 템플릿(카탈로그/산출물검색) |
  이슈/리스크 | 액션아이템 | 공문 | 회의록 — 동료 UI 메뉴 구조 계승

## 조작면 완결성(placeholder) 정책 (2026-07-07 확정)
읽기 전용 Phase 1이라도 **동료 UI에 존재하는 조작(버튼)은 신규 버전에도 노출**한다 —
제품이 뭘 할 수 있게 될지가 화면에서 보여야 한다. 동작은 3분류:

| 분류 | 처리 | 대상 |
|---|---|---|
| (a) Phase 2 연동 예정 | 버튼 노출 + 클릭 시 alert "🔧 준비 중 — 백엔드 연동 후 활성화됩니다 (Phase 2)" | 프로젝트 생성/수정, 이슈·액션아이템·공문·회의록 등록/수정/삭제, 산출물 전이(제출/승인/보완), 테일러링 선택 저장 |
| (b) 아마란스 위임 | 버튼 노출 + alert "📁 파일 기능은 아마란스(원챔버) 연계로 제공 예정입니다" | 템플릿/산출물 파일 등록·수정·다운로드·일괄 다운로드. 파일명/버전 컬럼은 표시하되 값은 '아마란스 연동 예정' |
| (c) 의도적 제외 | 버튼도 만들지 않음 | AI 포털, JSON 백업/복원 |

- 공통 헬퍼 하나(`stub(category, action)`)로 처리 — 문구 하드코딩 산발 금지.
- 참고: 동료 버전도 템플릿 다운로드를 alert 시뮬레이션으로 처리 중 — 동일 UX 톤.

## 동료 버전과의 차이 (의도적 변경 — 되돌리지 말 것)
1. **템플릿 화면**: 동료 버전은 템플릿 분류 선택 시 산출물 파일이 바로 나열된다.
   신규 버전은 분류 선택 → **업무 프로세스(ACTIVITY→TASK)가 먼저** 보이고 산출물은
   TASK 아래에 달린다(P1-3). 산출물만 모아 보는 건 별도 검색 메뉴(P1-4)로 분리.
2. **템플릿의 정의**: 산출물 파일 목록이 아니라 프로세스+상태전이+산출물의 묶음.
   화면·용어·데이터 접근 모두 이 정의를 따른다.
3. **템플릿 파일 업로드/미리보기/일괄다운로드는 구현하지 않는다** (2026-07-06 결정):
   산출물 파일 저장은 아마란스(원챔버)가 담당 — PMS는 파일서버를 직접 구축하지 않는다.
   카탈로그의 template_file_ref는 아마란스 파일 참조용으로 예약(연계는 0005 이후).
4. **AI 포털은 반영하지 않는다** (2026-07-06 결정): 실기능이 아니므로 제외.
   대시보드(P1-1.5)만 계승.
