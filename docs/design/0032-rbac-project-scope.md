# 0032 — RBAC 데이터 스코프: 권한 있는 프로젝트만 접근·수정 (설계 보충)

- 상태: 확정(너울님 2026-07-26) / 구현: impl/0035-rbac-scope
- 선행: 0031(RBAC 5역할·자체 로그인), 0005 §G(pms_user.person_id ↔ pms_person 연결)
- 배경: 0031은 **메뉴(URL prefix) 수준** 가드만 정의했다. 유경님에게 전달받은 권한 체계
  원자료(메뉴별/OPMS/프로젝트 데이터 매트릭스)에 따르면 **역할별로 접근 가능한 프로젝트의
  범위**와 **수정 가능한 데이터의 범위**가 별도로 정의되어야 한다. 본 문서가 그 보충 설계다.

## 1. 역할 정의 (원자료 확정본)

| 역할 | 정의 |
|---|---|
| SYS_ADMIN | 시스템 전체 관리 — 사용자·권한 관리, OPMS 방법론 CRUD, 모든 프로젝트·산출물 접근 |
| EXEC_ADMIN | 사업관리 총괄 — 전체 프로젝트 관리, 인력관리, 공문, 보고서. 방법론은 조회만 |
| PM | 자신이 **참여한** 프로젝트 관리 — Action Item·회의록·리스크·산출물 작성, 프로젝트 멤버 관리 |
| WORKER | 자신에게 **배정된 업무** 수행 — 담당 Action Item 수정, 담당 산출물 작성, 프로젝트 정보 조회 |
| VIEWER | 읽기 전용 — 수정·삭제 불가 |

## 2. 스코프 판정 키

- **참여(member)**: `pms_user.person_id` = `pms_project_member.person_id` (is_active=1)인 프로젝트.
  - person 연결: V22 자동 백필(조직 미러 `mber_id`=username → 이름 유일 매칭) + 관리자 콘솔 > 사용자에서 수동 연결.
  - person 미연결 사용자는 참여 판정 불가 → 참여 스코프 역할(PM/WORKER)에서는 **빈 목록**(오탐 방지, 정직한 실패).
- **담당(PM인) 프로젝트**: 참여 중이면서 `is_project_manager=1`.
- **본인 담당 항목**: 태스크·Action Item·산출물 등의 `assignee_name` = 연결된 person의 `name`.
  - 한계: 현 데이터 모델이 담당자를 이름 문자열로 저장(0022) → 동명이인 시 과허용 가능.
    후속: assignee에 person_id 병기(0022 개정) 시 정밀화.
- 적용 조건: `rbac.enforce=true` + 로그인 세션 존재 시에만. 개방 모드(비로그인 허용)에서는 미적용.

## 5. 시행 지점 (구현 설계)

시행 계층은 3단: **① 전역 인터셉터 → ② 리소스 가드 → ③ 목록 필터**.

### ① RbacInterceptor (전역, URL 수준)
- 기존(0031): SYS_ADMIN 전용 prefix, 쓰기 로그인 필수.
- 추가: `VIEWER + 쓰기 메서드 → 403` (전 API 일괄).
- 추가: OPMS 마스터 조회 제한 — `GET /api/catalog/nodes*`, `GET /api/doc-templates*`를
  WORKER/VIEWER에 403 (EXEC_ADMIN/PM은 조회 통과, 쓰기는 기존 SYS_ADMIN 가드).

### ② ProjectScopeService (리소스 가드)
- `assertCanView(ctx, projectId)`: PM/WORKER가 비참여 프로젝트 상세·하위 리소스 접근 시 403.
  적용: `GET /api/projects/{id}` 및 프로젝트 하위 읽기(상세 셰이프에 포함되는 범위는 상세 가드로 갈음).
- `assertCanEditProject(ctx, projectId)`: 프로젝트 자체 수정(PATCH·삭제·전환·상태 변경).
  PM=담당(is_project_manager=1)만, WORKER 403.
- `assertCanEditItem(ctx, projectId, assigneeName)`: 프로젝트 하위 항목 쓰기(태스크·이슈·
  Action Item·산출물·회의록 등 작업면 전반). PM=참여 프로젝트, WORKER=참여 + 본인 담당
  (assigneeName이 연결 person 이름과 일치)일 때만. assignee가 없는 항목(회의록 등)은
  WORKER의 경우 참여 프로젝트면 허용(✏️ 참여 프로젝트 준함).
- 인력관리(`/api/persons`, `/api/project-members`): VIEWER 403(조회 포함),
  PM/WORKER 조회는 참여 프로젝트·본인 범위(1단계는 서버 목록 필터 없이 화면 접근 제어,
  2단계에서 서버 필터 — §7).

### ③ 목록 필터
- `GET /api/projects`: PM/WORKER → 참여 프로젝트만 (VIEWER·관리자 전체).
- 대시보드 집계·전역 목록(이슈/Action/공문/회의록 메뉴): 1단계는 프로젝트 목록과 동일한
  참여 필터를 적용(참여 project_id IN 조건), 구현 편의상 미적용 구간은 §7 백로그에 명시.

### 프론트(메뉴 표시 정합)
- 사이드바: 역할 기준 숨김 — 테일러링·산출물 관리(WORKER/VIEWER), 인력관리(VIEWER),
  관리자(SYS_ADMIN만, 기존). 입찰 관리(WORKER).
- 서버가 최종 방어선(프론트 숨김은 UX용) — 직접 URL 접근은 서버 403이 막는다.

## 6. 사용자 관리 화면 (SYS_ADMIN)

- 관리자 콘솔 > 사용자: 목록(검색 q=아이디/이름/이메일, 역할 필터, 페이징 규약 준수),
  행 편집 — 역할 변경, 활성/비활성, **person 연결**(참여 스코프 판정 키), 비밀번호 발급(0034 API).
- 자기 자신의 SYS_ADMIN 해제·비활성화 차단(잠금 사고 방지).
- API: `GET /api/admin/users`(q, role, page, size) / `PATCH /api/admin/users/{id}`(role,
  isActive, personId) / `POST /api/admin/users/password`(기존).

## 7. 단계 구분

- **1단계(이번 impl/0035)**: §5 ①②③ 중 — VIEWER 전역 쓰기 차단, OPMS 마스터 조회 제한,
  프로젝트 목록 필터·상세 가드, 프로젝트 수정(담당 PM) 가드, 작업면(태스크·이슈·Action·
  산출물·회의록·공문) 쓰기 가드(PM 참여/WORKER 본인 담당), V22 person 백필,
  사용자 관리 화면, 사이드바 메뉴 정합.
- **2단계(백로그)**: 전역 목록(이슈·Action·공문·회의록 메뉴)의 참여 필터 서버 적용,
  인력관리 목록의 참여·본인 서버 필터, 회의록 "참석" 판정(참석자 명단 기반),
  assignee person_id 병기(동명이인 정밀화), 대시보드 집계 스코프.
