## 1. ⚠️ [최우선] OPMS 방법론 대형 신규 — 카탈로그/산출물/워크플로 도메인 병렬 재구현 (07-23)

관련 커밋: `f6d5f3b`(마이그레이션 스위트) · `ce5221d`·`28a306c`·`be0aafb`·`62ea2a8`·`c63bac4`·
`1b205b3`·`3f5cebb`·`d4e7246`(RLS/보안/검증 보강) · `924e91f`·`ecee358`(방법론 탭 UI) ·
`7bfe3aa`·`5f1308c`·`2279a40`·`61be7c4`(OPMS 대시보드/UI) · `f6d5f3b`

① **기능 요약**: 동료가 레거시 `/`(app.js + Supabase)에 **"OPMS 공공 SI 표준 수행방법론"**
(PRR~PED 6단계, 18 액티비티, 40 산출물)을 신규 구축. `supabase_migrations/`에 정식
마이그레이션 스위트(001 DDL·002 Seed·003 RLS·004 Verify)를 도입하고, **12개 테이블**을 생성:
- **마스터**: `methodology_templates`(code/version/status DRAFT·PUBLISHED·RETIRED) →
  `methodology_stages` → `methodology_activities` → `methodology_artifact_templates`
  (is_mandatory) + `methodology_project_types`(project_type별 기본 템플릿 매핑)
- **프로젝트 인스턴스**: `project_methodologies`(테일러링: tailored_by/at) →
  `project_methodology_activities`(status NOT_STARTED·IN_PROGRESS·IN_REVIEW·APPROVED·EXCLUDED) →
  `project_artifacts`(assignee_id·doc_number·exclusion_reason·계층 무결성 트리거)
- **저장·버전·결재**: `artifact_documents`(storage_bucket/path·**ai_generated·ai_model·ai_prompt·
  prompt_version**) · `artifact_versions` · `artifact_workflows`(PENDING·IN_PROGRESS·APPROVED·
  REJECTED·CANCELLED·current_step) · `artifact_workflow_steps`(REVIEWER·APPROVER·NOTIFIER 단계결재)
- **보안**: `approve_workflow_step()` SECURITY DEFINER RPC(결재는 RPC로만) · 모든 함수
  `search_path=public,pg_temp` 고정 · 계층 무결성 트리거(project_artifact가 자기 프로젝트의
  methodology/activity에 속하는지 검증) · RLS는 `project_members JOIN resources ON r.id=pm.resource_id`
  로 프로젝트 멤버십 + role(ADMIN/SYS_ADMIN/EXEC_ADMIN) 기준.

② **영향 영역**: [pms_* 스키마] + [dataClient 계약] + [UI] + [배포/마이그레이션] — **전 영역**.

③ **판단 제안**: **⚠️ 충돌/중복 — 설계 반영·정합 결정 최우선**. 이 12테이블은 우리 설계의
**핵심 도메인 전체와 정면으로 겹친다**:
- `methodology_templates→stages→activities→artifact_templates` = 우리 **산출물 카탈로그 마스터
  트리**([0010](../0010-schema-refinement.done.md), `pms_catalog_*`).
- `project_methodologies`(테일러링) + `project_methodology_activities` + `project_artifacts`
  = 우리 **테일러링 + `pms_deliverable`**.
- `artifact_workflows`/`workflow_steps` + `approve_workflow_step` RPC = 우리 **워크플로/상태전이
  ([0009](../0009-workflow-editor.done.md), `pms_workflow`/transition) + 공문 결재라인**([0024] "0005 이후").
- `artifact_documents`(storage·ai_generated) = 우리 **파일 저장([0018](../0018-file-storage.md)
  FilePort/NAS)** + AI 생성 산출물.
- status enum `NOT_STARTED/IN_PROGRESS/IN_REVIEW/APPROVED/EXCLUDED` = 우리 산출물 상태머신과 대조 필요.

  **결정 필요**: (a) 레거시 OPMS 방법론 모델을 우리 Spring/MariaDB 설계로 **흡수/매핑**할지, 아니면
  (b) 우리 기존 카탈로그·워크플로 설계로 대체할지. 어느 쪽이든 **PRR~PED 6단계·18액티비티·40산출물
  시드**와 **artifact 상태 5종**, **단계결재(REVIEWER/APPROVER/NOTIFIER)** 구조는 우리 설계에
  없던 구체 업무 지식이라 반드시 반영 검토. 플랫폼(Supabase RLS/RPC)은 우리가 Spring 단일화
  확정([0013])이라 **직접 이식 대상 아님** — 단, 계층 무결성 규칙·RPC 전용 결재·역할 스코핑은
  설계 참고 가치 높음. → **신규 설계 문서(예: 0025 방법론/OPMS 정합) 착수 권장.**

## 2. notifications 테이블 신규 + Action Item DB 파이프라인 정합 (07-22)

관련 커밋: `416d780`(notifications DDL) · `4747e64`·`b0b2559`·`e0b0ae5`·`057453e`·`72dcaff`·
`117d1b7`·`db53109`·`47fc63d` 외 Action Item assignee UUID 정합 다수.

① **기능 요약**: Action Item의 담당자(assignee)를 이름 문자열이 아닌 **profiles UUID**로 엄격
해석하도록 전면 정합(목록·상세·대시보드·AI 포털 공통 헬퍼 `getActionItemAssigneeName`,
`normalizeActionItemFromDb`). 신규 `notifications` 테이블(recipient/sender UUID·type·title·message·
`action_item_id`·is_read·RLS는 recipient=auth.uid())과 크로스세션 알림 추적, 읽음처리 RPC 도입.

② **영향 영역**: [pms_* 스키마](알림 테이블) + [dataClient 계약](액션아이템 assignee shape).

③ **판단 제안**: **설계 반영 권장**. `notifications` 스키마는 우리 설계에 아직 명문화된 알림
테이블이 없다(신호규칙 [0007]은 지표→액션, 코멘트 [0010]은 스레드). 동료 구현
(recipient/sender/type/action_item_id/is_read)을 우리 알림 설계의 입력값으로 반영하고,
[0002 §3.4](../requirements/0002-parity-features-clarification.md)의 "게시판 답변 알림"과
동일 알림 채널로 통합할지 검토. assignee=UUID 원칙은 우리 [0005] 단일 사람 마스터 방향과 일치.

## 4. 문의 게시판 신규 (07-10) — 0024 §B 캡처, 요구방향과 스키마 불일치 주의

관련 커밋: `a88b57e`(게시판 CRUD + 답변 + `migration_board.sql`).

① **기능 요약**: `board_posts`(category·title·content·status·author_id/name) +
`board_replies`(post_id·content·author) 신규. 관리자/PM 실시간 답변(댓글).

② **영향 영역**: [pms_* 스키마].

③ **판단 제안**: **정합 검증 권장 + ⚠️ 요구방향 불일치**. 레거시 구현은
`category` = **question/bug/suggestion/etc**, `status` = **pending/answered**이고 **공지·상단고정
컬럼이 없다**. 그런데 [0002 §3](../requirements/0002-parity-features-clarification.md)과 0024 §B는
**"공지/문의/일반 + 공지 상단 고정(외부 문의 창구)"** 방향으로 확인 요청 중이다. 즉 **실제 레거시
빌드 ≠ 확인요청 방향**. 유경님 회신으로 카테고리·상단고정·외부접근 권한을 확정한 뒤 `pms_board_*`
스키마를 맞춰야 한다(현 레거시 DDL을 그대로 미러하면 요구방향과 어긋남).
